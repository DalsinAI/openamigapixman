# pixman.library 1.0 and 2.0 on AmigaChrome, 17 October 2026

- **Machine:** lab t4-g-px, a copy of Instance-32. Its CPU is the AC090 with a 68040 profile and the JIT, and the board is ACRTG 64 MiB. It runs AmigaOS 3.2.3 on the stock 3.2.3 ROM.
- **Software:**
  - opengpu.library 0.16 from openamigartg `pixman/passthrough-20261017` (stream v1.4) for all three runs;
  - ACRTG.gpu as deployed, which knows stream v1.3. So COMPOSITE_PD batches run on opengpu.library's 68k back end, and FILL and COPY reach the host.
- **Method:**
  - PixBench, the binary unchanged from 1.0 (sha256 700fed88…), 640×480 at 32 bits;
  - three rounds, each round 1.0 then 2.0 with ACRTG.gpu, then 2.0 with ACRTG.gpu moved aside (the 68k back end only);
  - the lab restarted before every run.
- **Results:**
  - medians of the three, in µs a call;
  - every run passed PixBench's checks with the same final hashes (`a766e705` / `2fbe3ea7`);
  - the raw output is in `20261017-2.0-{before,gpu,cpu}-ac090-68040.txt`.

## What the figures say

- **Fills are faster.** Through ACRTG.gpu, FILL runs on the host, so fills and rectangle fills are 2.5 and 7 times faster than 1.0.
- **Composites are slower for now.** COMPOSITE_PD runs on the 68k until the host has stream v1.4 (DESIGN.md, gap 10). Upstream Pixman, built with GCC 16 and run by the JIT, does them 1.4 to 3.4 times faster than OpenGPU's 68k back end, which the os32 stove builds with GCC 6.5.
- **COPY through ACRTG.gpu is slower than on the 68k** for Fast RAM images: 1,120 µs against 723. That is OpenGPU's host path, not pixman.library's.
- **The runs vary.** Single runs of the same setup differ by up to 2 times on this lab.
